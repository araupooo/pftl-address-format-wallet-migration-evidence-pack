# Risk register
Risks from the address-collision and confusion analysis (docs/risk-analysis.md). Severity and likelihood are the pack's own judgement, grounded in the measured drill and cross-check results.
| ID | Severity | Likelihood | Risk | Finding | Detail |
| --- | --- | --- | --- | --- | --- |
| R-01 | HIGH | LIKELY | Wrong-curve import lands funds on a different, empty account | F-01 | Same seed, different curve = different address. A user importing a seed into a wallet that defaults to the other curve sees an empty account and may conclude the funds are lost, or send funds to the wrong-curve address. Recovery needs the seed + the other curve's derivation, which a panicked user may not know exists. |
| R-02 | HIGH | LIKELY | X-address sent to the node or stored as an account identifier | F-02 | The node has no X-address code and answers actMalformed. Any tooling that persists X-addresses as account IDs, or passes them to account_info / payment construction, breaks. The break is loud (an error) rather than silent, which limits the damage. |
| R-03 | HIGH | POSSIBLE | Testnet/mainnet address reuse: same classic address, two ledgers | F-03 | Classic addresses carry no network byte, so an address valid on the testnet is equally valid on mainnet. A payment built for one network and signed for the other is a user error the format cannot catch. X-addresses are the only format that distinguishes networks, and the node does not accept them. |
| R-04 | MEDIUM | POSSIBLE | Destination tag lost when a payment is addressed classically | F-10 | Tags live only in X-addresses. A flow that drops the tag (or assumes tag 0) when converting to a classic address sends an untagged payment to a tagged destination; the funds arrive but cannot be attributed by the recipient. |
| R-05 | MEDIUM | POSSIBLE | Mnemonic / BIP44 migration produces a different account | F-05 | The node has no mnemonic support; mnemonic wallets derive by their own path. Importing a mnemonic into a family-seed wallet (or vice versa) yields a different address, with the same empty-account confusion as R-01. |
| R-06 | MEDIUM | POSSIBLE | Ordinal-family accounts dropped in an Ed25519 migration | F-08 | secp256k1 seeds can hold many accounts (ordinals); Ed25519 seeds hold one. A migration that enumerates ordinals for an Ed25519 seed finds nothing, and one that assumes a single account for a secp256k1 seed can strand ordinal-1+ accounts. |
| R-07 | MEDIUM | UNLIKELY | Signing-digest implementation error produces rejected signatures | F-04 | secp256k1 signs SHA-512-Half(message); Ed25519 signs the message. Signing the bare signing hash fails verification for both curves (measured). The failure is loud (rejected signature), so the damage is a broken integration, not lost funds. |
| R-08 | MEDIUM | POSSIBLE | Seed-format confusion (family seed vs RFC1751 words vs hex) | F-05 | One 128-bit seed has four serializations (family seed, 12 words, 32 hex chars, passphrase). parseGenericSeed accepts all of them, and a passphrase that happens to look like a seed is treated as one. Users can mistake one form for another; the 12-word form has parity protection, the others do not. |
| R-09 | LOW | UNLIKELY | Single-character address corruption passes the checksum | F-12 | The 32-bit checksum catches a random corruption with probability 1 - 2^-32. Across all 1,938 single-character corruptions of a 34-character classic address, ~4.5e-7 are expected to pass. Negligible per address, non-zero across a large user base; copy-paste and QR codes are the practical mitigation. |
| R-10 | LOW | NEGLIGIBLE | AccountID hash collision | F-12 | 160-bit AccountID space: collision probability is ~3.4e-31 at 1e9 accounts and ~0.39 only at 2^80 accounts. Not a realistic risk; the confusion risks are encoding-level, not collisions. |
| R-11 | LOW | POSSIBLE | Special-address confusion (zero vs account-one) | F-09 | The zero address and the account-1 address are easily confused in documentation and code; both return actNotFound on the testnet. Neither holds funds, so the impact is limited to misleading documentation and tests. |
| R-12 | MEDIUM | LIKELY | No operator documentation for address formats | F-06 | With /docs/ returning 404 and the whitepaper silent on formats, operators learn the formats from code or from this pack. Undocumented formats invite the implementation errors in R-01, R-02, R-05, and R-07. |
| R-13 | LOW | LIKELY | wallet_propose unavailable through the public proxy | F-07 | Operators who expect the node to propose wallets get HTTP 403. Low impact (client libraries exist), but it is a trap for migration tooling written against a local node and then pointed at the public proxy. |
| R-14 | INFO | LIKELY | Validator master-key addresses are identities, not accounts | F-12 | All 25 validator master keys map to valid classic addresses, but none holds an account on the testnet (actNotFound). Tooling must not assume an address implies an account; conversely, funds sent to such an address would create an account controlled by the validator's master key. |
